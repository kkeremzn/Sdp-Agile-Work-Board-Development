    Widget Kurulum Sihirbazı

    Bu widget'ı bu SDP kurulumuna bağlamak için aşağıdaki 7 adımı, sırasıyla tamamla. Sıra önemli — sonraki adımlar öncekilerde oluşturduğun şeylere ihtiyaç duyuyor.

    1- Teknisyen Rolü Oluştur (AgileTechnician)

    Bunu en başta yapıyoruz çünkü aşağıdaki adımlarda bu role izin vereceğiz — önce var olması lazım. ⚙️ Admin → Users & Permission → Roles → New yolunu izle ve rol adını birebir "AgileTechnician" yaz. Requests tarafında teknisyenin widget üzerinden kendisine atanmış işleri görüntüleyip güncelleyebilmesi için gerekli View + Edit erişimini ver; Add verme. General Delete Permissions bölümünde genel silme izinlerini açma; teknisyen arayüzünde silme/yönetim operasyonları zaten rol bazlı olarak sınırlandırılır. "Technicians allowed to view = Assigned to him [Requests only]" ayarı Role oluşturma ekranında görünmüyorsa burada arama; bu ayar SDP sürümüne/kurulumuna göre ayrı bir Request erişim kapsamı ayarı olabilir. Kullanılabiliyorsa sunucu tarafında teknisyenin yalnız kendisine atanmış Request'leri görmesi için Assigned to him [Requests only] seçilmesi önerilir. Role ekranında ayrı bir Tasks → View/Edit bölümü yoksa ayrıca aramana gerek yoktur; widget'taki Subtask, SDP tarafında Request altındaki native Task kaydıdır ve erişim SDP'nin native Request/Task yetkilendirme modeliyle çalışır. Custom Module izinlerini 3. adımda vereceğiz. Kaydet ve widget'ı kullanacak her teknisyene AgileTechnician rolünü ata; "My Tickets" görünürlüğü bu rol adına bağlıdır.

    2- (Önerilir) Support Group Oluştur — İşleri Kime Atayabileceğini Sınırlar

    Bu adım neden var? Varsayılan olarak, widget'taki "Atanan Kişi" listesi tüm teknisyenleri gösterir. Eğer sadece belirli bir ekip bu widget'ı kullanacaksa (örn. "Yazılım Ekibi"), işleri yanlışlıkla ilgisiz bir teknisyene atamayı önlemek için bir Support Group oluşturup, birazdan (3. adımda) bunu bir kritere bağlayacağız — o zaman dropdown'larda sadece grup üyeleri görünür. İstemezsen bu adımı atlayabilirsin, o zaman tüm teknisyenler seçilebilir kalır.

    ⚙️ Admin → Users & Permission başlığı altında "Support Groups"'a git → "New" ile yeni bir grup oluştur, adını hatırlayacağın bir şey yap (örn. "Agile Board Ekibi") → 1. adımda AgileTechnician rolünü atadığın teknisyenleri bu gruba üye olarak ekle → kaydet.

    3- Dört Custom Module Oluştur

    SDP'nin Sağ üstündeki ⚙️ (Admin) ikonuna tıkla → açılan menüde "Developer Space" başlığı altında "Custom Modules"'a tıkla → hemen ardından "New" butonuna bas. Aşağıdaki 4 modülü, her biri için ayrı ayrı, bu adımı tekrarlayarak oluştur.

    Her modülde: Display Name ve Plural Name kutucuklarını doldur (örn. Display Name: Epic, Display Plural Name: Epics; SDP API Name değerlerini otomatik üretir) → Type olarak "Web Tab" seç → Fields List ekranında aşağıdaki alanları + New Field ile tek tek ekle → son olarak Permissions sekmesine geç. Dört Custom Module'ün tamamında (Space, Epic, Sprint, Widget Setting) SDAdmin = All Operations ve AgileTechnician = All Operations olarak yetkilendir. AgileTechnician'a Custom Module seviyesinde All Operations verilmesi, widget'ın ihtiyaç duyduğu API çağrılarının SDP permission hatasına takılmaması içindir. Yönetici/teknisyen ayrımı ve teknisyenin kullanabileceği işlemler widget arayüzünde rol bazlı olarak sınırlandırılır. Bu nedenle Custom Module permission katmanı API erişimini sağlar; widget UI yetkilendirmesi hangi işlemlerin kullanıcıya sunulacağını belirler.

    💡 "Assignee" alanları için: Aşağıdaki tabloda Space ve Epic'in Assignee alanını oluştururken, alan tipini "Reference Entity" seçip kaynak olarak "Technician"'ı işaretle. Eğer 2. adımda bir Support Group oluşturduysan, aynı ekranda "Criteria" (Kriter) diyen bir bölüm daha çıkar — oraya "Group is [senin grubun]" şeklinde bir kural ekle. Bu, o alanın dropdown'ında sadece grup üyelerinin görünmesini sağlar — widget bunu otomatik okuyor, ekstra bir ayar yapmana gerek yok.

    Modül Oluşturulacak Alanlar ve Tipleri
    Space Name (Single Line) ve Primary Field, Key (Single Line — "Mark As Mandatory" olarak işaretle, widget de zaten bunu zorunlu tutuyor), Description (Multi Line),
    Assignee (Reference Entity → Technician — yukarıdaki 💡 notuna bak, istersen Support Group kriterini burada da uygula),
    Sahip (Single Line — kimlik doğrulama fallback’i için zorunlu; teknisyen rolünde salt-okuma kullanıcı doğrulaması çalışmazsa widget bu alana küçük bir nonce yazar ve SDP response'undaki updated_by teknisyenini okur. Bu işlem Request/ticket oluşturmaz.)
    Epic Name (Single Line) ve Primary Field, Description (Multi Line),
    Status (Pick List — seçenekleri tek tek ekle: Open, Assigned, In Progress, Onhold, Resolved, Closed),
    Space ID (Single Line), Assignee (Reference Entity → Technician — yukarıdaki 💡 notuna bak, Support Group kriterini mutlaka buraya uygula, widget'ın Atanan Kişi listesi doğrudan bu alanın kriterini okuyor)
    Sprint Name (Single Line) ve Primary Field, Goal (Multi Line — Mark As Mandatory olarak işaretle), StartDate (DateTime), EndDate (DateTime),
    ActualStartDate (DateTime), ActualEndDate (DateTime), ClosureSummary (Multi Line),
    Status (Pick List — DİKKAT: Epic'ten farklı, sadece 3 seçenek: Future, Active, Closed — Sprint'in kendi yaşam döngüsü ticket'lardan farklı, "Assigned/Onhold/Resolved" gibi ara durumlara ihtiyacı yok),
    Resolution (Multi Line), Space ID (Single Line)
    Widget Setting Name (Single Line) ve Primary Field, Description (mutlaka Multi Line seç, Single Line seçersen kayıt "çok uzun" hatası verir)
    Bu modül, şu an doldurduğun bu sihirbaz formunun kendisini SDP'de saklamak için kullanılır.
    Zorunlu bootstrap standardı: bu modülün API Plural Name değeri cm_widget_settings, Description alanının API adı description olmalı. Yeni kullanıcı ilk açılışta config endpoint’ini ancak bu sabit adla bulabilir.

    3.5- Epic ve Sprint için Comments ve Attachment Yapılarını Ekle

    Widget'ın Epic/Sprint sohbet (chat) özelliği için ilgili Custom Module'de Sub Entities → Comments yapısını etkinleştir. Dosya ekleri için Attachment'ı Sub Entity altında arama; modülün Fields / Attachment Field bölümünden Attachment Field ekle. Aynı yapılandırmayı hem Epic hem Sprint için uygula.

    💡 Özet: Comments = Sub Entity; Attachment = Attachment Field. Comments için Maximum Records Allowed değerini kurumun beklenen sohbet hacmine göre belirle. Mentions, Reactions ve Replies temel widget sohbet akışı için zorunlu değildir.

    Custom Module Permissions: Space, Epic, Sprint ve Widget Setting modüllerinin tamamında SDAdmin = All Operations ve AgileTechnician = All Operations ver. Bu, API çağrılarının permission hatasına takılmaması içindir; teknisyenin yapabileceği işlemler widget UI/rol mantığında sınırlandırılır.

    Request/Ticket tarafında ekstra Custom Module Attachment kurulumu yapılmaz. Widget SDP'nin native Attachments ve Notes mekanizmalarını kullanır. Widget'taki Subtask, SDP tarafında ilgili Request/Ticket altındaki native Task kaydına karşılık gelir; Subtask chat/yorum akışı Task comments yapısını kullanır.

    4- Ticket Şablonunu Oluştur

    Yine ⚙️ Admin → "Templates&Forms" başlığı altında "Incident Templates"'e tıkla → "New Template" ile yeni bir şablon aç, adını (örn. SDP Agile Board Template) hatırlayacak şekilde yaz.

    SDP, yeni bir şablona otomatik olarak birçok hazır alan (Requester, Category, Group, Site, Impact, Urgency, Mode vb.) ekler — bunların çoğuna ihtiyacımız yok. Şablon düzenleme ekranında, formdaki alanların üzerine gelince çıkan çöp kutusu ikonuyla, aşağıdaki üçü dışındaki her hazır alanı formdan çıkar: Technician, Status, Priority (bu üçü kalsın). Sonra sol taraftaki "Available Fields" panelinin en sağından "+" ikonuna basarak, kendi custom alanlarımızı oluşturup forma sürükle:

    ⚠️ Önemli istisna: Yukarıdaki 💡 notundaki "Support Group kriteri" yöntemi, şablondaki hazır (native) Technician alanına uygulanamıyor — SDP bu alanı özelleştirmeye izin vermiyor, o hep tüm teknisyenleri gösterir. Bu widget'ta iş atamaları zaten Epic/Space'in Assignee alanına değil, ticket'ın kendi Technician alanına yazılıyor — yani kriter kısıtlaması sadece widget'ın kendi dropdown'ında geçerli olacak, SDP'nin native ekranında değil. Bunu bilerek ilerle, pratikte bir sorun yaratmıyor çünkü ekip zaten widget üzerinden çalışıyor.

    • Work Item Type — Pick List, Bu Alanı "Mark As Mandatory" olarak işaretle ve seçenekleri tek tek ekle: Story, Task, Bug
    • Sprint ID — Single Line
    • Epic ID — Single Line
    • Space ID — Single Line

    5- Her Alanın Gerçek API İsmini Bul

    Oluşturduğun her modül/alan için SDP kendi kendine bir "API Name" üretir — bu senin yazdığın isimden farklı olabilir (bazen bir alt çizgi "_" ekler, bazen eklemez). Formda ilgili alana tıkladığında, o alanın ayar ekranında "API Name" yazan gri kutuyu göreceksin. O değeri kopyalayıp aşağıdaki ilgili kutuya yapıştır.

    6- Bulduğun Tüm API İsimlerini Aşağıya Gir

    Yukarıda oluşturduğun her şeyin gerçek API adını buraya gir, sonra "Kaydet ve Başlat"a bas. Custom module için SDP'nin gösterdiği Plural ve Singular API adlarını ayrı ayrı kopyala; widget bunları tahmin etmez.

    7- Son Kontrol — Müşteriye Vermeden Önce

    Kaydetmeden önce aşağıdakileri tek tek doğrula. Bunlardan biri eksikse uygulamanın belirli bir bölümü çalışmayabilir:

    • AgileTechnician rol adı birebir aynı olmalı; plugin manifestindeki “My Tickets” görünürlüğü bu role bağlıdır.
    • Rolde Requests için gerekli View + Edit erişimi bulunmalı, Add verilmemeli ve General Delete Permissions açılmamalı. Assigned to him [Requests only] ayarı ortamda ayrıca sunuluyorsa Request kapsamını sunucu tarafında daraltmak için kullanılmalı; Role ekranında görünmüyorsa orada aranmasına gerek yoktur.
    • Dört Custom Module'ün tamamında SDAdmin = All Operations ve AgileTechnician = All Operations olmalı. Space üzerinde Sahip Single Line alanı bulunmalı; kimlik fallback’i bu alan üzerinden çalışır.
    • Sprint modülünde Goal alanı Multi Line + Mandatory; StartDate, EndDate, ActualStartDate, ActualEndDate alanları DateTime; ClosureSummary alanı Multi Line olmalı. Start/End planlanan zamanı, ActualStart/ActualEnd gerçek başlatma-kapatma anını tutar.
    • Epic ve Sprint'te Comments yapısı etkin olmalı ve dosyalar için Attachment Field eklenmiş olmalı. Attachment, Sub Entity olarak eklenmez. Request/Ticket tarafı SDP'nin native Notes + Attachments mekanizmasını; Subtask tarafı native Task kaydını kullanır.
    • Incident Template içinde native Technician, Status, Priority alanları ve custom Work Item Type, Sprint ID, Epic ID, Space ID alanları bulunmalı.
    • Support Group kullanıyorsan Epic Assignee Reference Entity alanındaki kriteri gruba bağla; widget teknisyen listesini doğrudan bu alanın native seçenek endpoint'inden okur.
    • Widget Setting dahil dört Custom Module'de AgileTechnician = All Operations olmalı; teknisyene sunulan gerçek işlemler widget UI/rol mantığında sınırlandırılır.
    Kaydet butonu boş API alanlarını engeller; ancak SDP tarafındaki alan tipi, pick-list değerleri ve rol izinleri API üzerinden güvenli biçimde otomatik değiştirilemediği için yukarıdaki son kontrol yine zorunludur.
